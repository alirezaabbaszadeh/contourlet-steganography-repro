# Dedicated FINAL-5J-v1 Runner Boundary

This document defines the next implementation package and prevents accidental extension of the historical 64/88-row runtime.

## 1. Separation rule

The existing `research_runtime.py` and its locked C0–C3, 16-embedding, 64/88-evaluation contract remain historical infrastructure. The 5J runner must be implemented in a new module and command path. It may reuse generic immutable-store, checkpoint, monitor, and atomic-write primitives, but it must not change the identity, object paths, counts, or reports of the previous run.

Proposed implementation paths:

```text
src/ctsteg/digital_ad/runtime_5j.py
scripts/5j/run_research.py
scripts/5j/research_status.py
```

## 2. Authoritative input

The runner accepts exactly one frozen expanded execution plan generated by `scripts/5j/build_execution_plan.py`. It must not derive extra tasks from directory contents, CLI flags, failed results, or observed outcomes.

Before scheduling any task it verifies:

- execution plan schema and plan ID;
- exact 530/8,420 counts;
- source/config/manifest/seed/baseline fingerprints;
- current checkout and adapters match the recorded fingerprints;
- all pair files match manifest SHA-256 values;
- transform/runtime/stability gates pass;
- remote backup backend is writable and restore-verifiable;
- `science_ready=true` from the input validator.

## 3. Task states

Each plan task has an append-only attempt history and one canonical state:

```text
planned
running
local_validated
backup_pending
committed_complete
scientific_failure
operational_failure
blocked
```

Scientific failure is a complete scientific observation and must progress through remote backup to `committed_complete`. Operational failure is retained as an attempt object but does not silently replace the planned task; retry policy is bounded and explicit.

## 4. Internal embedding tasks

For C0, C1, C2, C3_NP, and C3:

1. load and verify cover/secret bytes;
2. instantiate the task-specific config, including target PSNR;
3. encode format-v2 payload at the declared fraction;
4. verify actual protected bits equal the expanded plan;
5. build the exact variable-size slot plan;
6. perform embedding and realized PSNR/quality checks;
7. perform clean extraction as an embedding acceptance check;
8. write canonical embedding object, stego image, bitstream manifest, coefficient-map identity, runtime, and provenance;
9. atomically validate and checkpoint;
10. synchronously enqueue/perform remote backup and do not acknowledge completion until verified.

## 5. Baseline embedding tasks

B1/B2 execute only through approved adapters with frozen contracts. Each adapter must implement a common typed interface and expose:

- exact source/adapter fingerprint;
- input and payload preparation;
- embedding with distortion control;
- extraction/decoding;
- common metrics;
- unsupported semantic fields as `not_applicable`;
- deterministic artifact/provenance export.

No internal Base/Detail metric is fabricated for a non-layered baseline.

## 6. Evaluation tasks

An evaluation task references one committed embedding object and one frozen channel instance. It:

1. verifies embedding object and stego SHA-256;
2. derives/checks the pair-specific attack seed;
3. applies exactly the declared channel;
4. performs extraction with the declared payload fraction;
5. writes validity, S0–S6 stage, common metrics, failures, runtime, and provenance;
6. for internal methods, writes normalized header/Base/Detail codeword diagnostics and ECC overload;
7. for baselines, writes available common diagnostics and `not_applicable` fields;
8. backs up and verifies the complete evaluation evidence before completion acknowledgement.

## 7. Cache identities

Embedding and evaluation cache keys are the plan-provided content identities. The runner refuses:

- an object at the expected path whose canonical identity differs;
- a result generated by a different source/config/adapter/manifest/seed fingerprint;
- an object marked complete without a matching verified backup-ledger record;
- a duplicate result with divergent content;
- an unplanned task.

## 8. Resume and retry

Resume scans plan identities and immutable objects, not log text. A cache hit requires local schema/hash validation and verified remote backup identity. Incomplete temporary directories are quarantined. Operational attempts use bounded retry; permanent configuration, licensing, checksum, schema, scientific-gate, or identity failures remain fail-closed.

## 9. Reporting and monitoring

Live status separates:

- planned, running, local-valid, backup-pending, and committed tasks;
- embeddings and evaluations by component;
- scientific versus operational failures;
- current stage throughput and ETA after sufficient completed samples;
- backup queue depth, throughput, and verification failures;
- disk, memory, CPU, and worker utilization.

`committed_complete`, not local computation, is the progress numerator.

## 10. First acceptance target

Before connecting to the final server, the runner must pass a synthetic fixture containing:

- two engineering-only pairs;
- C0, C3_NP, C3 and two synthetic baseline adapters;
- clean plus one deterministic and one stochastic channel;
- at least two payload fractions and two PSNR targets;
- forced process termination and resume;
- remote filesystem backup, local deletion, restore, and hash verification;
- one scientific failure and one operational failure;
- deterministic typed analysis input generation.

This fixture is not scientific evidence and never enters the 50-pair result set.
